### 1. P1 · High — generated steps break the kvcr scripts by running `envsubst` on every `$` variable
`deployment-customizer.ts:1579`
- The code correctly works out `templateVars` without looking inside block scalars (1570–1574), but then runs bare `envsubst < agg.yaml`.
- With no format argument, GNU envsubst replaces every `$VAR`, so the runtime shell variables in the container scripts become empty.
- The repo's own `kvcr/deploy.sh:98-107` passes an explicit variable list for exactly this reason.
- Embedded in `kvcr.mdx`.

**Repro:** generated steps for `examples/backends/vllm/deploy/kvcr/agg.yaml`, then those steps emulated (no `envsubst` binary here):
```
envsubst < agg.yaml | kubectl apply --namespace "$NAMESPACE" -f -
44: 'state_namespace=$DYN_NAMESPACE' -> 'state_namespace='
59: 'if [ "$POD_INDEX" = "0" ]; then' -> 'if [ "" = "0" ]; then'
132: --kv-transfer-config "$kv_transfer_config" -> ""
```
`agg-memory-service.yaml` loses `PYTHONPATH`, `KVCR_READY_TIMEOUT_SECONDS` and `kv_transfer_config` the same way.

**Fix:**
```diff
- `envsubst < ${manifestFile.name} | ...`
+ `envsubst '${templateVars.map(n => `\${${n}}`).join(" ")}' < ${manifestFile.name} | ...`
```

### 2. P1 · High — download Job hangs when the manifest itself defines the PVC
`deployment-customizer.ts:1662` and `1552–1558`
- When the claim is in `info.claims`, `createPvc` is forced to false, so `model-cache.yaml` contains only the Job.

- The Job pod stays Pending until the 60-minute timeout.
- This happens with the default UI settings: an existing PVC selects `pvc` mode with the download Job on.

**Repro:** `examples/backends/trtllm/deploy/disagg-multinode.yaml` (PVC `models` at lines 67–75, embedded in `multinode.mdx`) produces:


**Fix:** when `info.claims.includes(claim)`, apply the manifest before the Job wait, or copy that PVC document into `model-cache.yaml`.
